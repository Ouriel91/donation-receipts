# Donation Receipts product policy

The final human decisions below govern this candidate. Historical test sources remain available, with conflicting expectations recorded in the release audit test dispositions.

1. Use the strict final QA3/MANUAL receipt evidence policy. An unlabelled numeric filename alone cannot supply a receipt ID.
2. Classify receipt and tax confirmation separately. An unrelated identifier cannot fill a missing receipt ID. Leave unsupported values empty and preserve protected publication decisions.
3. A missing, malformed or unexplained proof on an independently inactive archive row is a diagnostic, not a publication veto. Preserve its marker, data and inactivity. A hidden unowned row with a retained archive marker stays inactive. An active identity/index conflict or genuinely unsafe active document binding still fails closed. No adoption of unexplained inactive values into active totals. Proven v1 upgrades and journaled v2 annotations remain available.
4. PDF success means the correct verified source opens in Windows Excel. Native paths and file URIs are both admissible representations.
5. Diagnostics must be accurate. Legacy labels and exact log formatting are superseded.
6. Preserve legacy migration and its tests outside the release. Existing validated QA3 already has the RC user/account layout. Production migration independence is unconfirmed. The recovered Production launcher predates the RC user-scoped entry point. Direct Production transition needs a separate, local check that the existing state already satisfies the RC user marker, mailbox ownership, account tree, catalog and PDF paths. If those conditions fail, the current release has no approved transition path. No migration is included or executed.
7. Compact ORIGINAL/COPY pairing accepts only an entirely numeric PDF stem followed immediately by O or C, case-insensitively. The complementary file must have the exact same digit string, including leading zeros. A lone COPY marker, prefixes, collision suffixes and compact nonnumeric endings cannot supply a pair. An explicit separated ORIGINAL or COPY label can supply a role within a shared name, under the same evidence rules. Role labels identify candidates only. Both current PDF contents must independently provide the same unambiguous strict extracted receipt number, corroborated by organization, amount and date, with no conflicting fields or protected distinct decision. The numerical filename stem is never treated as the receipt number. Both automatic and reviewed paths apply the source checks. An eligible pair counts once, prefers COPY, and retains both PDFs, protected corrections, approvals and archived publication history. Existing archived publications are not reopened.

8. **Apply receipt content before ORIGINAL/COPY names.** Independently verify unambiguous receipt numbers from both current PDF contents and corroborate them with organization, donation date and amount. Reject conflicting evidence, ambiguous sources and protected distinct decisions. Only after identity is established, classify role names under decision 7. An authenticated original Gmail attachment name bound by the saved PDF SHA-256 and account can supply the role when a generated local filename lacks one. An original name and an eligible saved name that disagree leave the role ambiguous. Names never supply receipt-number evidence. Prefer COPY, retain both PDFs and count one donation when the pair qualifies. Same-byte, explicit decisions and general verified identity remain separate mechanisms. When Full reconciles active publications, generic cross-PDF archival must leave rejected or ambiguous ORIGINAL/COPY claims separate for review.
9. **Use the dynamic COMBINED canonical name.** The scoped annual publication is `donation_{year}_combined.xlsx`. Normal publication recognizes a preceding generated COMBINED file, carries forward its IDs, and verifies byte equality before retiring the prior name. Different bytes under both names stop publication without overwriting either. COMBINED consumes effective source publications under its existing cross-account aggregation rules, retaining both source publications, verified links, manual protections and provenance. Aggregation based on those published values does not assign a copy role or archive a source publication. It can consult the two candidate PDFs to choose a representative for a qualifying cross-source O/C pair. This decision does not authorize migration of user or account state or operator-side Production access.

## Implemented extraction decision order

1. **Read and normalize.** `receipt_summary._extract_row` calls pypdf and uses raw and Hebrew-normalized text. It also tries PyMuPDF when pypdf processing reaches that step. A higher count of populated amount, date, receipt, organization registration and tax fields changes the provisional reader preference. Ties retain pypdf. `_best_metadata` prefers raw for registration/donor values and normalized for receipt/tax/date/amount, and preserves non-missing-field notes. Both readers' available text variants go through the final evidence resolver. This is corroboration and conflict detection, not a requirement that both readers succeed or agree on every nonempty field. An early pypdf exception in the shared `_extract_row` takes its unreadable path. MANUAL also probes each reader separately for document type and diagnostics; that probe does not replace the shared extractor's failure handling. There is no OCR.
2. **Identify other fields first.** In `receipt_metadata_extractor.extract_metadata`, obtain organization registration, provisional tax and labelled donor ID. Detect a full tax label before the legacy tax patterns. Strip the recognised tax field span before searching for a receipt and exclude known registration, donor and legacy/short tax values. A distinct, independently labelled receipt and full tax field can contain the same characters. The full tax span itself cannot supply a receipt. A short legacy tax label is conservatively excluded by value. When configured donor evidence supplies a donor ID in PRIMARY, the shared second pass excludes it before publication.
3. **Search for a receipt in text.** `_find_receipt_number_in_text` tries direct and reversed receipt-specific labels first, then supported donation headings and adjacent/reversed numeric layouts. These include `מספר קבלה`, `קבלה מס׳`, `קבלה #`, labelled `קבלה על תרומה` and visual Hebrew variants. `_additional_receipt_numbers` adds dashed headings, supported marked or visual copy/original forms, and labelled RC tokens. Normalized text is preferred in the provisional extraction, with raw as fallback. The shared reader pass then revisits labelled text across the available engines before trusting a filename candidate.
4. **Use a filename only as a constrained fallback.** `_find_receipt_number_from_filename` requires one unambiguous receipt-labelled candidate in the filename. The text must already provide registration, a date and an amount. The filename's underscores are treated as spaces. Unlabelled digits never qualify, including when other donation fields are present. A stronger text candidate overrides the filename. A separate date-from-filename fallback exists in the shared extractor. MANUAL checks and rejects a filename-derived date for automatic publication.
5. **Validate and reconcile.** `_valid_receipt_number` and `_additional_identifier_is_valid` require a digit, reject excluded IDs and disallow partial token matches at word and separator boundaries. Depending on the label, they reject date/year shapes, short decimal amounts, page counts or a wrapped number belonging to another labelled field. An unmarked bare numeric donation heading does not authorize hybrid suffix guesses. `resolve_identifier_evidence` strips direction marks, deduplicates text variants, and collects observed template evidence, explicit labelled receipts, institution suffixes and lower-priority heading evidence. Explicit evidence takes precedence over generic heading evidence. Multiple competing candidates for the same field, or an existing conflict note, clear that field and mark it for review. One valid explicit receipt can replace a provisional value. If no acceptable receipt survives, the field stays empty. Missing receipt/tax can be partial metadata rather than a substituted number.
6. **Resolve tax separately.** `_full_tax_fields`, `_observed_tax_fields` and `_visual_tax_numbers` recognise the full Hebrew reporting confirmation label, reverse reader order, nearby labelled allocation, and supported reported-donation forms. A value must be adjacent to evidence from that layout. Legacy matching accepts supported 3–8 digit forms near the tax authority/report label, excluding plausible years. On observed receipt layouts the strict candidate set supersedes provisional legacy guesses; a lone one- or two-digit non-institution token is a review candidate, not a published tax value. Conflicting tax candidates clear tax independently of the receipt number. Bare page numbers and values attached to an intervening receipt heading do not count. Outside observed layouts, the shared resolver can retain a recognised legacy provisional value where no contradictory evidence replaces it.
7. **Institution-specific scope.** `_institution_headers` requires the supported institution marker and matching receipt pattern within the same document section. The full slash serial stays in `full_source_serial`; the suffix alone becomes the receipt number and retains leading zeros. A conflicting serial is a receipt review condition. A valid short tax field in this institution layout may publish as confirmed. `_payment_totals` accepts one verified payment-block total; competing totals remain for review. MANUAL `_inspect` independently checks the corresponding receipt date through `_rivhit_dates` and requires one valid date and amount. Payment-only dates cannot fill the receipt date.
8. **Apply publication controls.** PRIMARY uses the shared reader plus scoped catalog and publication controls. MANUAL uses the same identifier resolver, adds PDF signature, genuine-receipt/non-summary, organization and date/amount review gates, and preserves the supplied intake name when the physical file has been renamed. An ambiguous receipt ID queues review. An empty receipt ID can pass only if there is still qualifying receipt evidence and the remaining gates pass. `sync_state._refresh_identifiers` proposes corrections against the actual published field. `sync_workbook.sync_approved_identifiers` checks the document SHA, prior publication value and protection before publishing an approved change; conflicts, comments/formulas and untracked ownership are handled through review. MANUAL decisions and exclusions remain in the same private existing paths. Re-extraction cannot automatically replace protected published identifiers.

## Evidence and version changes

The final QA3 and RC MANUAL intake and inspection module bytes match. RC added Phase 5 optional scope-field compatibility, short legacy tax exclusions and the conservative bare numeric heading guard. RC4B changed historical workbook and sync rules only. It does not change institution parsing, approved ID workflow or MANUAL gates.

### Final O/C evidence and deployment implications

[_oc_role, _oc_pdf_evidence, _original_copy_pairs and reviewed_oc_pair](../src/sync_workbook.py) implement the shared rule. [Targeted tests](../tests/test_final_oc_policy.py) cover names, source evidence, COPY, preserved corrections and repeat runs. The decision applies to the actual saved basename. The existing Gmail saver can add a date/label prefix or a collision suffix. A resulting basename outside this rule stays outside compact pairing. No source renames or storage behavior changed. An already applied historical review remains in its existing ledger. An unapplied old review relying on an ineligible basename or unverified receipt can halt Full at the stale review gate. Check that condition locally if QA3 reports it. No older approval is deleted or silently reapplied.
